# 第一章 MySQL架构

## 数据库与数据库实例

- 数据库：操作系统文件，或其他形式文件的集合。在MySQL中，可以是frm、MYD、ibd结尾的文件。
- 数据库实例：**MySQL数据库实例在系统上的表现就是一个进程，**是程序，是位于用户与操作系统之间的一层数据管理软件，任何对数据的操作都是在数据库实例的控制下进行的。

## 架构

![MySQL-架构](pics/MySQL-架构.webp)

MySQL数据库区别于其他数据库最重要的一个特点就是其插件式的表存储引擎。

需要注意的是，存储引擎是基于表的，而不是数据库。

## 存储引擎

- InnoDB：当前默认引擎，特点是支持事务，行锁，支持使用外键，并支持无锁读
- MyISAM：以前的默认引擎，特点是不支持事务，表锁，并支持全文索引
- NDB：特点是数据全放内存中，处理起来很快

# 第二章 InnoDB存储引擎

> InnoDB是第一个完整支持ACID事务的MySQL存储引擎，其特点是行锁设计、支持MVCC、支持外键、提供一致性非锁定读。
>
> 被设计用来最有效地利用内存和CPU。

## 一条更新语句的执行过程

![更新语句执行过程](pics/更新语句执行过程.png)

**注意上述浅色部分是在 InnoDB 引擎内部完成的，而深色部分是在执行器当中执行的**。

更新流程设计两个重要的日志模块：Redo Log 和 Bin Log。

Redo Log 是 InnoDB 引擎独有的，而 Bin Log 是 MySQL 服务层实现的，所有存储引擎都可以使用。

当一条更新语句经过连接器、查询缓存、分析器、优化器达到执行器时，执行流程如下：

1. 通过引擎取出符合条件的记录，如果符合条件的记录数据页就在内存中，则直接返回给执行器，否则引擎会从磁盘读入数据到内存中，再返回给执行器；
2. 执行器拿到引擎给的数据，进行更新操作，再调用引擎接口写入新数据；
3. 引擎将数据更新到内存，同时将更新操作记录到 Redo Log，此时 Redo Log 处于【prepare】状态，之后通知执行器执行完成，随时可以提交事务；
4. 执行器生成该操作的 Bin Log，并把 Bin Log 写入磁盘；
5. 调用引擎的提交事务接口，引擎把刚刚写入的 Redo Log 改成【commit】状态，更新就完成了！
6. 数据不会立即被更新到磁盘中，而是会在合适的时候，异步刷盘。

Redo Log 必须经过两阶段提交，是为了让 Redo Log 和 Bin Log 之间保持一致，从而保证数据库在崩溃后进行恢复的时候，由 Redo Log 恢复的主库，和由 Bin Log 进行主从复制时的从库保持数据一致。

## InnoDB VS MyISAM

- InnoDB 支持事务，MyISAM 不支持
- InnoDB 支持表锁、行锁，后者只支持表锁
- InnoDB 支持外键
- MyISAM 崩溃后发生损坏的概率比前者高，并且数据恢复的速度也慢
- MyISAM 支持压缩表和全文索引
- 对于查询操作频率远大于更新操作的业务场景，且不需要事务支持，可以选后者

# 第三章 索引

## 为什么选择 B+ 树

核心原因：面向磁盘，在面向磁盘进行读写操作时，B+ 树有着更高的性能。

索引除了 B+ 树的实现外，还有 AVL 树，红黑树、B 树，为什么 MySQL 选择了 B+ 树作为索引结构的底层实现？

- AVL 树：追求绝对平衡，每次修改都需要进行若干次旋转来保持平衡
- 红黑树：追求相对平衡，在有限次数内而不是每次都保持平衡
  - AVL 树和红黑树都是二叉树，随着存储数据量的增加，树的高度随之增加，不利于磁盘 I/O，旋转操作过多也会导致写性能极差。
  - 所以二叉树天生不适合做大数据索引

- B 树：叶节点和非叶节点都存有数据，单页能存放的索引键变少，**树层高被迫增加**；进行范围查询时，每需要跨节点遍历，无法连续扫描
- B+ 树：非叶子纯索引，占用空间少，单页能放很多索引键，所以树高极低，可以减少 IO；叶子节点是有序双向链表，所以范围查询 、 排序都很方便，**完美匹配磁盘存储 + 数据库业务**，因此成为 MySQL 索引标配。

## B+ 树数据存储量计算（了解）

InnoDB中，默认页大小为 16KB，假设非叶节点保存的索引项大小占 16B，则一页大概可以保存1000条索引项，假设叶节点保存的数据项平均为 160B，则一页大概可以保存 100 条记录。

对于 3 层的 B+ 树而言，数据量级是： 1000 * 1000 * 100，大概是 10 ^ 8 条，千万级别。

对于 4 层的 B+ 树而言，数据量级是： 1000 * 1000 * 1000 * 100，大概是 10 ^ 11 条，百亿级别。

## B+ 树索引

B+ 树是大多数 MySQL 存储引擎的默认索引类型。在创建表时，如果有多个索引，MySQL 就会同时维护多个 B+ 树：

- **聚簇索引**：主键查询时，就会走聚簇索引，按照主键 ID 进行升序排序，叶节点中存储完整记录。由于主键是必须的，所以聚簇索引也是必有的
- **二级索引**：如果表存在普通索引，那么就会维护对应数量的二级索引，在叶节点中存储普通索引值和主键 ID，并按照普通索引值进行升序排序。如果要查询的数据不是或不仅是主键ID，那么就可以通过主键 ID **回表**到**聚簇索引**找到完整记录，如果查询的数据只包括当前索引和主键 ID，不需要回表，就叫**索引覆盖**
- **联合索引**：在叶节点中存储多个普通索引值和主键 ID，并按照普通索引的设定顺序依次进行升序排序，主键 ID 同样是为了进行回表操作。由于是按照普通索引的设定顺序依次进行排序，第二个索引是在第一个索引排好序的情况下再排序的，所以联合索引在进行查询时，WHERE 语句必须从左到右来匹配联合索引的顺序，这就叫**最左匹配原则**

# 第四章 事务

## MySQL 事务的特性 - ACID

- 原子性（Atomicity）：要么全成功，要么都失败，不能只做一半。比如A给B转账，A扣钱，B加钱，不能说A钱扣了，B钱没加上
- 一致性（Consistency）：操作前后，数据永远合法合理。比如账户余额不能为负，转账前后总数不能变
- 隔离性（Isolation）：多个事务同时进行，互相不干扰。比如A转B的同时B转A，不会读取到对方中途未提交的数据
- 持久性（Durability）：一旦提交后，数据永远保存，就算出故障、断电也不会丢

## MySQL 如何保证事务的 ACID 特性？

- 原子性：通过 Undo Log 保证，因为它可以记录反向操作，提供了事务的回滚能力
- 持久性：通过 Redo Log 保证，在数据库崩溃后，可以通过重放 Redo Log 恢复数据库
- 隔离性：锁和 MVCC，锁可以看做悲观控制的模式，多版本并发控制可以看作乐观控制的模式
- 一致性：通过原子性、持久性、隔离性来实现最终一致性

## 并发事务的问题

- **脏读**：事务 1 把账户 A 的余额从 100 扣到 50，但还没提交。这时候事务 2 进来，读取到 A 的余额为 50，这时候事务 1 回滚了，A 的余额变回了 100，那么事务 2 读到的 50 
  就是脏数据，如果在这个基础上对账号 A 余额进行操作，就肯定会出错。所以，读到未提交的数据，就是脏读
- **不可重复读**：事务 1 读取账户 A 的余额为 100，此时事务 2 扣了 A 的余额 50，事务 1 再次读取 A 就只剩 50 了，表现就是事务 1 
  在同一个事同务中，两次读取的数据却不同。所以，读到别人已提交的修改，就是不可重复读
- **幻读**：事务 1 读取余额为 100 的所有账户，查到 1 条，这时候事务 2 又来搞事，新增了一条余额也为 100 的账户，事务 1 
  再读的时候，查到了两条，表现就是结果变了，像幻觉一样。所以，读到别人已提交的插入、删除，就是幻读
- **丢失更新**：账号 A 的余额现在是 100，事务 1 进来，扣他 50，准备写余额 50，事务 2 进来，也扣他 50，也准备写余额 50，两个都提交，最后 A 余额还是 
  50，就少扣了。所以，后提交的覆盖了先提交的修改，就是丢失更新

## 隔离性

基于锁和 MVCC 机制共同实现的。不同的隔离级别实现方式不一样：

- READ-UNCOMMITTED（读未提交）：最低的隔离级别，允许读取尚未提交的数据变更，可能会导致脏读、幻读或不可重复读
- READ-COMMITTED（读已提交）：允许读取并发事务已提交的数据，可以阻止脏读，但幻读或不可重复读仍有可能发生
- REPEATABLE-READ（可重复读）：对同一个字段的多次读取结果都是一致的，除非数据是被本身事务自己所修改，可以阻止脏读和不可重复读，但幻读仍有可能发生
- SERIALIZABLE（可串行化）：最高的隔离级别，完全服从 ACID 的隔离级别。所有的事务依次逐个执行，这样事务之间就完全不可能产生干扰，也就是说，该级别可以防止脏读、不可重复读以及幻读

## 丢失更新的解决方案

丢失更新属于写冲突，事务隔离级别无法解决，主要靠两个思路来解决：

- 悲观锁：`SELECT ... FOR UPDATE`，直接上行锁
- 乐观锁：用版本号来更新

## 锁

MySQL通过**读写锁**来实现并发控制：

- 共享锁（S 锁）：读锁，事务在读取记录时获取共享锁，允许多个事务同时获取
- 排它锁（X 锁）：写锁/独占锁，事务在修改记录的时候获取排他锁，不允许多个事务同时获取。如果一个记录已经被加排他锁，那其他事务不能再对这条记录加任何类型 锁
- 读写锁能做到读读并行，不能做到读写并行、写写并行

另外，根据锁粒度的不同，又被分为表级锁和行级锁

- 表级锁：一次锁一张表
- 行级锁：一次锁一行，InnoDB支持行级锁，粒度更小，所以对并发写入操作来说，InnoDB性能更高

## MVCC

MVCC是多版本控制方法，即对一份数据会存储多个版本，通过事务的可见性来保证事务能看到自己应该看到的版本。通常会有一个全局的版本分配器，来为每一行数据设置版本号，版本号是唯一的，从而保证提供读已提交和可重复读的能力。

# 第五章 日志

## Redo Log

为了更好的读写性能，InnoDB 会将数据缓存在内存中，对磁盘数据的修改也会落后于内存，这个如果进程或机器崩溃，会导致内存数据丢失。

为了保证数据库本身的一致性和持久性，InnoDB 维护了 Redo Log，修改 Page 之前需要先将修改的内容记录到 Redo Log 中，并保证 Redo Log 早于对应的 Page 落盘，也就是常说的 WAL，Write Ahead Log。当故障发生导致内存数据发生导致内存数据丢失后，InnoDB 会在重启时，通过重放 Redo，将 Page 恢复到崩溃前的状态。

设计有 prepare 和 commit 状态，可以知道一个事务是否已提交修改。

## Undo Log

直译为“撤销”，可以联想到 Windows 的 Ctrl + Z 操作，记录的是每个事务中所有更新语句的反向操作，它提供了事务的回滚能力。

## Bin Log

是一种逻辑日志，记录的是每一个更新操作（可以是更新 SQL 或更新行），通常用于主从复制时从库进行数据同步，以及将数据恢复到以往的某一时刻。
