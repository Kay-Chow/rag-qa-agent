# 第一章 Kafka 基础

## 什么是 Kafka？

Kafka 是一个高吞吐、分布式、发布订阅的流处理平台，一般用于日志收集系统和消息系统。

## 和其他消息队列相比，Kafka 的优势在哪里？

其实 Kafka 最初是设计用于日志系统的，但随着后续发展，Kafka 也变成了一个合格的消息系统，我理解它的主要优势有：

- 一个是 Kafka 是基于 Scale 和 Java 开发的，设计中大量使用了批量处理和异步的思想，最高可以处理每秒千万级别的消息。因此，Kafka 有着极致的性能
- 另一个就是 Kafka 的生态系统兼容性无可匹敌，尤其是在大数据和流计算领域，如 Spark

## 消息模型

### 队列模型

队列模型师最早的消息模型，使用队列作为消息通信载体，满足生产者和消费者模式。但是，一条消息只能被一个消费者使用，未被消费的消息在队列中保留，直到被消费或者超时。

它的主要问题是，如果我们要将生产者生产的消息完整地分发给多个消费者，队列模型就解决不了了，因为队列中的消息只能被消费一次。

### 发布订阅模型

在发布订阅模型中，消息的发送方称为发布者（Publisher），消息的接收方称为订阅者（Subscriber），服务端存放消息的容器称为主题（Topic）。发布者将消息发送到主题中，订阅者在接收消息之前需要先订阅 Topic，该消息将会通过 Topic 传递给所有它的订阅者。

在发布订阅模型中，如果只有一个订阅者，那它和队列模型基本就是一样的了。所以说，发布订阅模型在功能层面时可以兼容队列模型的。

Kafka 采用的就是发布订阅模型，其实 RocketMQ 的消息模型和 Kafka 也基本是一样的，只是 Kafka 中的队列被称为分区（Partition）。

# 第二章 Kafka 核心概念

## Kafka 的结构

- Producer：生产消息的一方，生产者
- Consumer：消费消息的一方，消费者
- Broker：代理，可以看做一个独立的 Kafka 实例，多个 Kafka Broker 在 Zookeeper 的维护下组成一个 Kafka Cluster。
  - Topic：主题，一个 Broker 中可以维护多个主题，Producer 将消息发送至特定的主题，Consumer 通过订阅特定的主题来消费对应的消息，在 Zookeeper 中的表现形式就是一个个文件夹
  - Partition：分区，每个 Topic 都可以有多个分区，分区的主要作用是做负载，来提高 Kafka 的吞吐量，可以把它理解为消息队列中的队列，在同一个 Broker 下的同一个 Topic 中，各分区的数据都是不重复的，在 Zookeeper 中的表现形式就是 Topic 文件夹下一层的文件夹

## Kafka 的多副本机制了解吗？带来了什么好处？

刚刚我们说了，一个 Kafka Cluster 中可以有多个 Broker，那么自然是要做主从的，但是 Kafka 集群中的主从不是以 Broker 为维度的，而是以副本为维度的。

每一个 Partition 都可以有多个副本，分散在不同的 Broker 中，作为备胎。在这些 Partition 副本中，会选举出一个 Partition 副本作为 Leader，其他的就被称为 Follower，这样的话如果 Leader 所在的 Broker 挂了，Kafka 就会从 Follower 中选举出一个作为新 Leader。这样就实现了自动的**故障转移**。

同时，在 Zookeeper 的协同下，Kafka 可以将不同的 Partition 分布在不同的 Broker 上，还可以根据负载来选举 Leader，这样就实现了**动态负载均衡**。

# 第三章 Kafka 核心机制

## Kafka 如何保证消息的消费顺序？

因为一个 Topic 下面可以有多个 Partition，可以看做有多个队列，如果是同一个队列中的消息，是可以保证顺序消费的。消息在被追加到 Partition 中时，会分配一个特定的偏移量（offset），Kafka就是通过 offset 来保证消息的顺序性的。

但如果是多个队列，Kafka 在生产消息的时候，可以指定 Partition，或者给消息设置一个 Key，同一个 Key 的消息一定会送到同一个 Partition 中，这样就能保证同类型的 Key 可以顺序消费了。

## Kafka 如何保证消息不丢失？

### 生产者丢失消息

生产者调用 `send` 方法发送消息后，消息可能因为网络问题并没有发送过去，所以生产者需要确认是否发送成功。需要注意的是，生产者调用 `send` 方法是一个异步操作，所以一般不推荐 `send` 之后主动去查询结果，可以添加回调函数，监控到发送失败就进行重试。

### 消费者丢失消息

我们知道，每个消息在 Partition 中都有一个 offset，而每个消费者也维护了一个自己的 offset，来标记自己消费到哪了。

当消费者拉取到了分区的某个消息后，默认会自动提交更新 offset。注意，这个时候消费者其实才刚拿到消息，还没开始消费呢，如过这时候消费者挂了，offset 却自动提交了，那消息就丢了。

解决办法也比较粗暴，咱把自动提交 offset 给关了就行了，每次都在真正消费完消息后再手动提交 offset。但是捏，有有新问题，如果你刚刚消费完某个消息，正准备提交 offset 呢，挂了。。那么再重启的时候，offset 未更新，理论上会消费该消息两次。这个时候就需要消费者这边自行做幂等校验来保证消息消费的可重入性了。

#### 那么什么时候用自动提交 offset 合适呢？

允许消息延时的场景，一般都会用自动提交。如果消息在消费者这丢了，可以通过定时任务进行补偿。

### Kafka 丢失消息

我们都知道，Kafka 多副本有着故障自动转移机制，当 Leader 挂掉时，就会从 Follower 中重新选举一个 Leader，这个时候如果 Leader 中的数据还没完全被 Follower 同步，就会造成消息丢失。

- 粗暴但有效的设置 acks = all：acks 默认值为 1，代表我们的消息被 Leader 副本接收之后，就算发送成功。这个时候如果Leader 挂掉了且消息还未主从同步，那就丢了。如果我设置 acks = all，就表示只有所有副本都接收到消息后，生产者才会收到来自服务器的响应。这种模式是最高级别的，最安全的，但延迟会高一点
- 更细致的设置：
  - 设置 replication.factor >= 3：这样就保证每个 Partition 至少有 3 个副本，
  - 同时设置 min.insync.replicas > 1：表示消息需要至少被写入到 2 个副本才算发送成功。该值默认为 1，在实际生产中应该尽量避免默认值为1；
  - 设置 unclean.leader.election.enable = false：直译就是不允许不干净的 Follow 进行 Leader 选举，这里不干净就是指主从同步程度不达到要求，这样就降低了消息丢失的可能性
  - tips：要确保 replication.factor > min.insync.replicas，如果你设置一个 Partition 有 3 个副本，却要求每次发送消息都至少同步给 4 个副本。。那完了

## Kafka 的重试机制

### 消费失败会怎么样？

默认配置下，消费异常会进行重试，重试多次后会跳过当前消息，继续进行后续的消费，保证业务的正常进行。

### 重试失败后被跳过的数据如何处理？

死信队列（Dead Letter Queue，DLQ），是消息中间件的一种特殊队列，如果一个消息被重试多次仍消费异常，就会被丢入死信队列，而不是永久性地丢弃。这样，我们就可以对死信队列中的消息做进一步处理。
