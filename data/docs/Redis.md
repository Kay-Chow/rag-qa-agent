# 第一章 Redis 基础

## Redis 为什么快？

- 面向内存处理数据
- 服务端单线程处理 Redis 指令，避免上下文切换以及锁竞争
- 基于单 Reactor 单进程的 I/O 多路复用模型
- 优化过常用的数据结构

## Reactor 单进程的 I/O 多路复用模型

需要从一条 Redis 指令的执行流程讲起：

![redis-单线程](pics/redis-单线程.jpg)

1. 读取 Socket
2. 解析请求
3. 执行内存 I/O
4. 写入 Socket

其中，读取 Socket 和写入 Socket 属于是比较耗时的网络 I/O 操作，相比之下涉及 Redis 数据操作的内存 I/O 耗时就要少很多了。

这个时候，Redis 在保持【**单线程**】进行数据操作的同时，将耗时的读取 Socket 操作、解析请求、写入 Socket 外包出去，由多个 I/O 线程来运行，而不怎么耗时的执行操作仍由**单线程**来运行。那么主线程只需要从多个 I/O 线程获取客户端指令，依次执行，然后交由多个 I/O 线程进行 Socket 写入。这就相当于通过**异步**的方式，大大提高了 Redis 服务的性能。

![redis-多线程](pics/redis-多线程.jpg)

# 第二章 常用数据类型

## String

虽然 Redis 是 C 写的，但是 Redis 并没有直接使用 C 的字符串来表示，而是自己构建了一种 **简单动态字符串**（Simple Dynamic String，**SDS**）。相比于 C 的原生字符串，Redis 的 SDS 不光可以保存文本数据，还可以保存二进制数据，并且获取字符串长度的复杂度为 `O(1)`（C 字符串为 `O(N)`），除此之外，Redis 的 SDS API 是安全的，不会造成缓冲区溢出。

- 首先需要认识一下 SDS 的结构：`int len`，`int free`，`char buf[]`

- 使用变量 `len` 用于记录长度，因此获取长度信息的时间复杂度为 `O(1)`，当然，len 的作用可不止于此

- 如果对 String 的修改操作会使得字符串长度增加，SDS 有一个**空间预分配**机制：
  - API 会先判断 buf 空间的大小是否满足，如果满足则直接操作，不满足则开始**空间预分配**
  - 如果修改后 SDS 的 `len` 小于 1 MB，程序直接给 `buf` 额外多分配一块和修改之后 `len` 一样大小的未使用空间，即修改完之后，len = free，同时 `strlen(buf) = len + free + 1`（这个 + 1 是 C 语言字符串结尾的 `\0` 哦，用于终止字符数组）
  - 如果修改后 SDS 的 len 大于 1 MB，那么程序会额外多分配 1 MB 的 `free` 空间，比如原数据是 5 MB，修改后是 6 MB，那么程序会直接将 `buf` 扩容达到 7 MB，其中 `len` 为 6 MB，`free` 为 1 MB
- 如果对 String 的修改会导致字符串缩短，SDS 又有一个**惰性空间释放**机制：
  - SDS 并不会直接回收多出来的空间，而是单纯地修改 `len` 和 `free`的值，`len` 相应减小，`free` 相应增大，`buf` 空间大小不变
  - 通过惰性空间释放，可以很好地减少缩短字符串所需要的内存重分配操作，而且多于的的空间在之后字符串增长的时候直接使用
  - 当然，SDS 也提供了直接释放未使用空间的 API，需要的时候可以直接使用
- C 字符串中的字符必须符合某种编码，比如ASCII，而且字符串除了末尾不能出现空字符，也就是刚刚说的 `\0` ，否则会被程序认为是字符串的结尾。所以 C 字符串只能用于存储文本数据，而不适合用来存储图像、音频等二进制数据。而 SDS 就可以不在乎这些，反正有 `len` 来指定存储数据大小；同时 SDS 操作的 API 都是二进制安全的

### 应用场景

- 存储：缓存 Session、Token、序列化后的对象等等
- 计数：简单限流，点赞数等

## List

Redis 中的 List 其实就是**链表**数据结构的实现。在 Java 中，内置 LinkedList 实现了链表，但是 C 并没有，所以 Redis 也是自己实现了一个链表，其结构为双向量表，支持反向查找和遍历，更方便操作，不过也带来了额外的一点内存开销。

### 应用场景

- 信息流展示：最新文章，最新动态等
- 消息队列：可以，但并不推荐，功能过于简单

## Hash

Redis 中的 Hash 是一个 String 类型的 field-value （键值对）映射表，适合存储对象。

底层结构的话，类似于 JDK 1.8 之前的 HashMap，内部实现也是数组 + 链表。

### 应用场景

- 对象数据存储的场景：用户信息、订单信息等

## Set

Redis 中的 Set 是一种无序集合，有点类似于 Java 的 HashSet，底层数据结构为字典，可以轻松实现交集、并集、差集的操作。

### 应用场景

- 需要存放的唯一数据的场景：点赞用户统计、访客统计
- 需要交集、并集、差集的场景：共同好友、音乐推荐
- 需要随机获取数据的场景：抽奖、点名

## Sorted Set

类似于 Set，但和 Set 相比，Sorted Set 多了一个权重参数，使得集合中的元素能够按照权重来进行排序，还可以通过权重范围来获取元素。

### 应用场景

- 根据权重进行排序的场景：微信步数排行榜、直播间礼物排行榜等
- 需要存储的数据有优先级：优先级任务队列

# 第三章 持久化

## RDB

### 什么是 RDB 持久化？

Redis 可以通过创建快照来获得内存中数据在**某个时间点**上的副本。Redis 创建快照后，可以对快照进行备份；可以将快照复制到其他 Redis 服务器，实现主从结构；还可以将快照留在原地以便重启服务器的时候使用。

快照持久化是 Redis 默认的持久化方式，在 redis.conf 配置文件中默认配置为：

```c
save 900 1           # 在900秒后，如果至少有1个key发生变化，Redis就会自动触发bgsave命令创建快照
save 300 10          # 在300秒后，如果至少有10个key发生变化，Redis就会自动触发bgsave命令创建快照
save 60 10000        # 在60秒后，如果至少有10000个key发生变化，Redis就会自动触发bgsave命令创建快照
```

可以看出，key变动得越频繁，创建快照的频次就会越高。

### RDB 创建快照时会阻塞主线程吗？

Redis 提供了两个命令来生成 RDB 快照文件：

- `save` ：同步保存操作，会阻塞 Redis 主线程
- `bgsave` ：fork 出一个子进程，由子进程来执行，不会阻塞 Redis 主线程，默认选项

## AOF

### 什么是 AOF 持久化？

除了快照机制，Redis 还可以通过类似于 Bin Log 的机制，保存每一条数据修改命令。

### AOF 工作基本流程

- 命令追加（append）：所有的写命令都会追加到 AOF 缓冲区
- 文件写入（write）：将 AOF 缓冲区数据写入 AOF 文件中。这一步需要系统调用 `write` 函数，`write` 将数据写入到系统内核缓冲区就就直接返回了。此时并没有同步磁盘
- 文件同步（fsync）：AOF 缓冲区根据不同的` fsync` 策略，来向磁盘做同步操作。这一步需要系统调用 `fsync` 函数，`fsync` 函数针对单个文件操作，对其进行强制磁盘同步，`fsync` 会阻塞至磁盘写入完成后再返回，保证了数据持久化
- 文件重写（rewrite）：随着 AOF 文件越来越大，需要定期对 AOF 文件进行重写，新的 AOF 文件会和原有 AOF 文件所保存的数据库状态一样，但体积更小，从而达到压缩的目的。
- 重启加载（load）：当 Redis 重启时，可以加载 AOF 文件进行数据恢复

## RDB VS AOF

### RDB 的优势

- RDB 文件存储内容是经过压缩的二进制数据，是一个快照，体积小，适合做数据备份和容灾恢复
- RDB 恢复时，直接解析数据并还原即可，而 AOF 需要依次执行每个写指令，慢多了

### AOF 的优势

- AOF 安全性更高，可以实时持久化数据，因为 AOF 每次只需要追加写一条命令，比快照要轻量很多。
- AOF 文件更易读，可以直接导出 AOF 文件进行分析，甚至可以通过修改 AOF 文件来进行一些类似于回滚的操作

### 综上

- Redis 保存数据丢失一些也没什么影响的话，可以只用 RDB
- 不建议单独使用 AOF，因为时不时创建一个 RDB 快照可以进行数据备份、更快的重启以及解决 AOF 引擎错误
- 如果对保存的数据要求安全性较高，建议同时开启 RDB 和 AOF 持久化
- 如果只是纯缓存，而不作为数据库使用，可以都不启用

# 第四章 性能优化

## Big Key

### 什么是 Big Key？

简单来说，如果一个 Key 对应的 Value 所占用的内存比较大，那么这个 Key 就可以当做是 Big Key。

### Big Key 是怎么产生的？

- 使用不恰当，比如用 String 类型存放二进制文件
- 业务考虑不周，比如使用 Set 时没考虑到数据量的快速增长
- 未及时清理垃圾数据，比如 Hash 中冗余了大量无用的键值对

### Big Key 的危害？

- Redis 客户端超时阻塞：由于 Redis 服务端是单线程处理，在操作 Big Key 时，就会阻塞 Redis，客户端就容易超时
- 网络阻塞：假设一个 Big Key 的大小是 1MB，每秒访问 1000 次，那么每秒就有 1000 MB 的流量，哈人
- 内存不足

### 如何发现 Big Key？

- `--bigkeys` 命令
- 开源工具分析 RDB 文件
- 公有云分析

### 如何处理 Big Key？

- 分割：将一个 Big Key 分割为多个小 Key
- 手动清理：Redis 4.0+ 可以使用 UNLINK 命令来异步删除 Key
- 采用合适的数据结构
- 开启 lazy-free（惰性删除/延迟释放）：Redis 4.0+ 之后引入的特性，可以让 Redis 采用异步方式延迟释放 Key 使用的内存，将该操作交给单独的子线程，避免阻塞主线程

## Hot Key

### 什么是 Hot Key？

如果一个 Key 的访问次数较多，且显然比其他 Key 多很多，那他就是 Hot Key。

### Hot Key 是怎么产生的？

主要是某个热点数据访问量暴增，如热搜、秒杀商品

### Hot Key 的危害？

Hot Key 一般都伴随着大量的请求，会占用大量 CPU 和带宽，可能影响 Redis 实例对其他请求的正常处理。此外，如果突然访问 Hot Key 的请求超过了 Redis 的处理能力，可能会把 Redis 打挂，然后大量请求会直接落到数据库上，进一步打挂数据库！

### 如何发现 Hot Key？

- `--hotkeys` 命令
- 开源工具
- 提前预估
- 业务代码记录
- 公有云，无敌！

### 如何解决 Hot Key？

- 主从架构：读写分离，主节点处理写请求，从节点处理读请求
- 使用 Redis 集群：将热点数据分散存储在多个 Redis 节点上
- 二级缓存：可以将 Hot Key 放本地内存中

# 第五章 缓存三问

## 缓存穿透

### 什么是缓存穿透？

简单来说，缓存穿透就是有大量的请求，它们的 Key 是不合理的，根本不存在于缓存中，也不存在于数据库中。这就导致了这些请求根本不会走缓存，全部打到了数据库上，给数据库带来了巨大的压力，甚至可能直接打挂数据库。

### 有哪些解决办法？

- 最基本的就是要先做好参数校验，比如查询数据库的 ID 不能小于 0、传入的邮箱格式不对，就直接返回对应的错误信息
- 然后就是可以考虑缓存无效 Key，如果缓存和数据库都查不到某个 Key，那么就在 Redis 中缓存一下该 Key。但是，如果有黑客恶意攻击，每次都用不一样的 Key，会导致 Redis 中缓存大量无效的 Key，很危险，内存可是很贵的。所以一定要设置过期时间，而且要尽量短一点。但是太短就会失去作用。。。所以不能从根本上解决缓存穿透
- 最合适的就是**布隆过滤器**了：布隆过滤器是一个数据结构，可以非常方便地判断一个数据是否存在于海量数据中。当我们在写入数据时，在布隆过滤器里做个标记，每次查询数据库前先查布隆过滤器，如果查询到数据没被标记，那么它一定不在数据库中。但是，由于布隆过滤器时基于哈希函数实现的，不同数据之间可能存在哈希冲突，造成误判的情况。所以，**查询布隆过滤器说数据存在，并不一定表面数据库中真的存在这个数据；但是如果查询到数据不存在，那数据库中就一定不存在该数据**
- 除此之外，还可以做一些接口限流，比如根据用户或者 IP 对接口进行限流，或者对异常频繁范围的行为，还可以把异常 IP 列入黑名单。当然，缓存三问，都可以配合限流来解决，毕竟都是因为流量过大

## 缓存击穿

### 什么是缓存击穿？

缓存击穿中，请求的 Key 对应的是热点数据，该数据存在于数据库中，但不存在于缓存中，通常是因为缓存中的那份数据已经过期。这就可能导致瞬时大量的请求直接打到了数据库上。

### 有哪些解决办法？

- 永不过期，设置热点数据永不过期，或者过期时间比较长，一看就不太合适
- 提前预热，针对热点数据提前预热，比如在秒杀场景中，提前缓存热点商品，并使数据在秒杀结束前不过期，很合理！
- 加锁，在缓存失效后，通过设置互斥锁，确保只有一个请求去查询数据库并更新缓存，也还行

## 缓存雪崩

### 什么是缓存雪崩？

简单来说，缓存雪崩就是指缓存在同一时间，大面积失效，导致大量请求都直接打到数据库上，跟雪崩一样。一般有两种情况，一种是 Redis 直接挂了，那自然雪崩，一种是大面积缓同时过期。

### 有哪些解决办法？

- 针对 Redis 服务不可用的情况
  - Redis 集群，避免单机出现问题导致整个缓存服务都无法使用
  - 多级缓存，设置多级缓存，例如本地缓存 + Redis 缓存的二级缓存组合，Redis 挂了还有本地缓存呢
- 针对大量缓存同时失效的情况
  - 设置随机失效时间，可以避免大量缓存同时失效，从而减少缓存雪崩的风险
  - 提前预热，跟缓存击穿一样，保证热点数据们在热点的时候不会过期
  - 永不过期，跟缓存击穿一样，不推荐，但对于某些关键性和变化不频繁的数据，可以考虑

## 分布式锁

### 分布式锁的误删除问题

如果分布式锁设置不合理，是可能导致误删除的。

- 分布式锁设定的 Value 都一样，导致 A 请求在获取锁后，操作时间过长导致锁被自动释放
- B请求过来，成功获取到锁，正操作着呢
- 这时候 A 又操作完了，操作完肯定是要主动释放锁的，它并不知道它自己的锁已经过期了，直接去尝试释放锁，结果把 B 的锁给释放掉了

解决方法：用 UUID 作为互斥锁的 Value，就能防止误删了。

# 第七章 Redis 集群

## Redis主从架构

> 主从架构和哨兵模式都不是Redis集群，但老师容易搞混，就都放这里了。

**一主一从或一主多从**，主要解决问题是读写分离、数据备份、故障兜底。没有数据分片，所有节点都存储全量数据，也没有自动故障转移，所以经常跟哨兵模式一起用。

## Redis Sentinel（哨兵模式）

### 什么是 Redis Sentinel？

Redis Sentinel 是 Redis 提供的高可用解决方案，它负责监控 Redis 主从架构中的节点状态，并在主节点发生故障时，自动将某个节点提升为主节点。这一过程被称为**故障转移**，Sentinel 保证了 Redis 服务的持续可用性，即使某个 Redis 节点崩溃也不会影响整个系统的运行。

### Sentinel 如何实现故障转移？

当 Sentinel 判断主节点确实下线后，会通过以下步骤执行故障转移：

- 从现有的从节点中选取一个最合适的候选者
- 将选中的从节点提升为新的主节点
- 更新其他从节点，让它们开始同步新的主节点
- 通知客户端，使其重新连接到新的主节点

### Sentinel 的选举机制？

在故障转移期间，Sentinel 会从从节点中选择新的主节点，选择的依据主要有：

- 数据复制延迟最小的数据尽量不丢失，且新的主节点能尽量快速地接管服务。

### Sentinel 可以防止脑裂吗？

并不能完全防止脑裂。脑裂是指由于网络分区，主从节点被错误地分为多个独立的主节点组。在极端网络条件下，Sentinel 仍可能出现脑裂现象，如果为了彻底避免脑裂，建议使用 Redis Cluster，它有更复杂的选举机制和通信协议，可以防止这一问题。

## Redis Cluster（集群模式）

### 什么是 Redis Cluster？

虽然 Redis Sentinel 解决了高可用性问题，但它并未解决 Redis 在单节点上的性能瓶颈和存储限制。Redis Cluster 则通过数据分片和分布式存储的方式，**多主多从**，突破了单节点的内存上限，同时实现了系统的横向扩展，适合高并发、大规模数据场景。

### Redis Cluster 的特性

- 数据分片：Redis Cluster 将整个 Key 空间划分为多个片段，将每个片段映射到一个特定的哈希槽上。集群中每个节点负责存储一部分哈希槽，从而实现了数据的分布式存储
- 节点互联与通信：Redis Cluster 中的节点通过 Gossip 协议进行通信，共享集群状态和元数据。这种节点互联机制确保了集群的灵活性与可扩展性。新节点可以轻松地加入或离开集群，而不会影响现有节点的正常运行
- 故障转移：Redis Cluster 采用了主从复制模式来确保数据的可靠性。每个主节点都有一个或多个从节点，他们会异步复制主节点的数据，就是 Redis Sentinel 的故障转移机制
- 负载均衡：Redis Cluster还提供了负载均衡机制，确保每个节点都承载大致相同的负载。客户端在发起请求的时候，会根据哈希槽和节点映射关系，选择一个合适的节点进行通信，这种设计使得 Redis Cluster 可以更高效地处理大量并发请求
