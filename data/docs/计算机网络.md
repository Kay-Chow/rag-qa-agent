# 第一章 计算机网络体系

## 常见的计算机网络体系结构

## 各层功能

互联网实际使用的模型是 TCP/IP 模型，分为四层：

- 最上层是**应用层**，负责 HTTP、DNS 等应用服务；

- 然后是**传输层**，通过 TCP、UDP 实现端到端传输；

- 再往下是**网络层**，负责 IP 寻址和路由；

- 最底层是**网络接口层**，负责硬件和数据帧传输。

- ## 分层的必要性


各层之间相互独立之后，每个层都可以采用最合适的技术来实现，灵活、方便、易实现，易维护，也容易形成标准。

## HTTP VS HTTPS

### 区别

- 端口不同，HTTP 80，HTTPS 443
- HTTPS在应用层HTTP协议和传输层TCP协议之间加了一个SSL/TLS协议，保证传输的安全性
- HTTP只需要三次握手之后便可以开始进行传输，后者在三次握手后还需要进行SSL/TLS握手才可以进入加密报文传输
- HTTPS需要向CA申请数字证书，来保证服务器身份是可靠的

### HTTPS解决的问题

- 混合加密实现机密性：
  - 使用非对称加密算法传递对称算法秘钥，使用对称加密算法传递HTTP报文
  - 非对称加密算法使用公钥和私钥解决了秘钥交换问题，但运算速度慢
  - 对称加密算法只使用一个秘钥，运算速度快，但秘钥必须保密，需借助非对称加密算法来进行安全的秘钥交换
- 摘要算法实现完整性
  - 常见摘要算法：MD5、SHA-1、SHA-256
- 数字证书实现真实性
  - 服务端所颁发的公钥被存放在数字证书中，一旦客户端验证服务端身份成功，即可取出公钥进行加密操作

## SSL/TLS协议

SSL 是旧版，TLS 是它的升级版，现在全网用的都是 TLS，大家习惯统称 SSL。

### TLS握手过程

- 第一步：客户端打招呼（Client Hello）
  - 告诉服务端，我支持哪些加密算法，并生成一个随机数client random给服务端
- 第二步：服务端打招呼（Server Hello）
  - 在客户端支持的加密算法中选定合适的算法，也生成一个随机数server random给客户端
  - 同时，服务端会把自己的数字证书也传给客户端
- 第三步：客户端验证证书
  - 客户端去找CA机构验证收到的数字证书，通过的话，从里面获取公钥
- 第四步：客户端生成预主秘钥（pre-master-key)
  - 生成预主秘钥后，用公钥加密传给服务端，这里是非对称加密算法，只有服务端私钥能解密
- 第五步：双方各自算出会话秘钥（sessionKey)
  - 客户端：client random + server random + pre-master-key -> 计算出主秘钥（masterKey) -> 从主密钥中生成会话秘钥
  - 服务端：用私钥解密出 pre-master-key，跟客户端一样获取会话秘钥
- 第六步：握手结束开始加密通信
  - 直接用会话秘钥进行对称加密

# 第三章 TCP

## TCP基本认识

- 面向连接：进程A在向另一个进程B发送数据前，两个进程必须先相互“握手”，来建立连接
- 双全工服务：当进程A和另进程B存在一条TCP连接，那么应用层数据既可以从A流向B，也可以从B流向A，且可能同时进行
- 最大报文段长度（Maximum Segment Size，MSS）：以太网链路层的最大传输单元为1500字节，运输层头部一般是20字节（即TCP头部），网络层头部一般也20字节（即IP头部），那么MSS的典型值就是1500-40=1460字节。在传输大文件时，TCP一般将文件划分为若干个长度为MSS的报文，并通过TCP头部的序列号和确认号来保证传输顺序以及完整性

### 头部格式

![TCP-HEADER](pics/TCP-HEADER.webp)

- 源端口号、目标端口号：被用于多路复用。不让数据迷路
- 序列号：用来保证传输的顺序
- 确认号：通知客户端还需要收到哪些序列号，用来保证传输的完整性
- 6bit的标志字段：
  - ACK位：用于指示确认号中的值时有效的
  - SYN位：用于三次握手，在第一次和第二次握手中，SYN被置为1，等成功进行到第三次握手时，SYN被置为0，表示连接已建立
  - FIN位：用于四次挥手，挥手时会发送FIN为1的报文
  - RST位：当客户端发送的报文服务端接收不了，就返回RST位为1的报文，告诉 客户端别发了，滚~

- 窗口大小：用于流量控制
- 选项：用于商量MSS到底多大

### TCP VS UDP

- 连接
  - TCP是面向连接的传输层协议，传输数据前需要先建立连接
  - UDP不需要建立连接即可传输数据
- 服务对象
  - TCP仅支持一对一的两点服务
  - UDP支持一对一，一对多，多对多的交互通信，因此可用于广播通信
- 可靠性
  - TCP是**可靠交付数据**的，数据可以无差错、不丢失、不重复、按需到达
  - UDP是**尽最大努力交付**，不保证可靠交付数据
- 拥塞控制、流量控制
  - TCP有拥塞控制和流量控制机制，增加数据传输的可靠性
  - UDP没有，即使网络拥堵，也不会影响UDP的发送频率
- 首部开销
  - TCP首部较长，有一定开销，一般没有选项字段时是20个字节，使用了选项字段则更长
  - UDP首部只有8字节，并且是固定不变的，开销较小，由源端口、目的端口、长度、校验和组成
- 传输方式
  - TCP是流式传输，没有边界，但保证顺序和可靠
  - UDP是一个包一个包的发送，有边界，但可能会丢包和乱序
- 分片不同
  - TCP传输文件如果大于MSS大小，则会在**传输层**进行分片
  - UDP报文如果大于MTU大小，则会在**网络层**进行分片
  - TCP是流式协议，消息无边界，理论上一个报文可以无限大
  - UDP是报文协议，消息有边界，由UDP首部中长度字段控制
- 应用场景
  - TCP：FTP文件传输、HTTP、HTTPS
  - UDP：DNS、视频和音频通信、广播

## 三次握手

<img src="pics/三次握手.webp" alt="三次握手" style="zoom:67%;" />

- 第一次握手：客户端发送SYN包后，状态转为【同步已发送】（SYN_SENT）
- 第二次握手：服务端收到SYN包后，返回SYN+ACK包，状态转为【同步已接收】（SYN_RCVD）
- 第三次握手：客户端接受到SYN+ACK包后，发送ACK包给服务端，两边状态都转为【已建立连接】（ESTABLISHED）

### 为什么是三次握手？

- 假设仅有两次握手：
  - 那么服务端在接收到客户端的SYN包后就会立刻进入ESTABLISHED状态。
  - 这种场景下，客户端开始向服务端发送SYN包
    - 第一个SYN包因为网络原因，没到达服务端
    - 那么客户端超时了，就会进行重试，又发了一个SYN包，这次建连成功了，收到了SYS+ACK包，进入ESTABLISHED状态。然后成功传输完数据，关闭连接，进入CLOSE状态
    - 此时，第一个SYN包化身奇迹行者，在野区终于刷完野了，回到服务端这里，服务端收到SYN包理解进入ESTABLISHED状态，而客户端处于CLOSE状态。。。客户端会丢弃服务端发的所有包。。。导致服务器一直处于ESTABLISHED状态，造成了服务端资源的浪费
  - 若是三次握手，服务端收到第一个SYN包，会进入SYN_RCVD状态，在未收到客户端ACK包的时候，会重发SYN+ACK包，当重发到一定次数时，会主动关闭连接，从而避免资源浪费
- 除此之外，三次握手还可以同步双方的初始序列号、确认号
- 三次握手理论上已经可以建立可靠连接，不需要四次了

## 四次挥手

<img src="pics/四次挥手.png" alt="四次挥手" style="zoom:67%;" />

- 第一次挥手：主动关闭方发送FIN包给对方，自己进入【终止等待1】（FIN_WAIT_1）
- 第二次挥手：
  - 被动关闭方收到FIN包，回复ACK包，自己进入【关闭等待】（ClOSE_WAIT），**表示被动方此时在等待进程调用`close()`函数关闭连接**
  - 主动关闭方收到ACK包后，进入【终止等待2】（FIN_WAIT_2），**表示主动方此时的【发送通道】已经关闭了**
- 第三次挥手：被动方在发送ACK包后，会继续处理数据，处理完毕之后也会发送FIN包，并进入【最终确认】状态，表示等待主动方返回的ACK包
- 第四次挥手：
  - 主动方收到FIN包，回复ACK包，进入【时间等待】（TIME_WAIT），在Linux下大约1分钟后，连接将会彻底关闭
  - 被动方收到ACK包后，连接会直接彻底关闭

### 为什么挥手需要四次？

- 通常服务端在收到客户端发送的FIN报文时，可能还会有一些数据未发送，因此先回一个ACK报文，等待自己这端的数据发送完毕后，才会发送FIN包。因此需要四次
- 但是，如果说服务端没有数据要发送，那么其实也会直接发送ACK+FIN包给客户端，这样只需要三次挥手就完成了双端关闭

### 为什么等待时间是2MSL？

- MSL（Maximum Segment Lifetime）：报文最大生存时间
- 假设客户端最后一个ACK包丢失（发出直到消亡1MSL），此时服务端超时重发FIN包（发出直到消亡1MSL），一来一回正好2MSL，如果这段时间内客户端都没有再收到服务端发送是FIN包，则直接进入CLOSE状态
- 当客户端重新收到服务端的FIN包时，会再次进行第四次挥手，返回ACK包给服务端，并重新计时2MSL
- Linux中1MSL为30秒，2MSL为60秒
- 为什么要掐死到2MSL？
  - 对客户端来说，TIME_WAIT状态过多，将**导致大量端口被占用，无法发起新连接**
  - 对服务端来说，TIME_WAIT状态过多，虽然服务端只监听一个端口，但是会把建立好的连接丢给后续线程处理，处于这样状态的连接线程越多，将**导致内存资源被占满，无法处理新请求**

### 为什么需要TIME_WAIT状态？

- 一是保证被动方的正常关闭，假设没有TIME_WAIT状态，最后一个ACK包丢失，被动方重传的FIN包无法得到回应，会导致被动方长时间处于LAST_ACK状态，占用系统资源
- 二是防止旧连接的数据包干扰新连接，2MSL足以让两个方向上的数据包都自然消亡，再出现的数据包一定是新建立连接产生的

## TCP可靠传输

> TCP是通过【序列号】、【确认应答】、【重发机制】、【连接管理】、【窗口控制】等机制实现可靠传输的

### 重传机制

- 超时重传：当此前数据包的ACK包不在RTO（Retransmission Timeout， 超时重传时间）内到达，将重传此前数据包，当再次超时，RTO将会翻倍，表示网络环境差，不宜频繁发送
- 快速重传：当发送端收到三个同样的ACK包时，会假定这些ACK指向的数据段丢失了，并立即重传这些丢失的数据段。相比超时重传，提高了数据传输的效率

### 滑动窗口

- 在没有滑动窗口之前，一个TCP数据包必须在上一个数据包的应答返回后，才能继续发送下一个包，数据包往返时间的越长，通信效率就越低
- 引入滑动窗口机制，发送方可以在接收方滑动窗口未被填满之前连续发送数据包
- TCP滑动窗口有两种：
  - 发送窗口：发送端的窗口，取决于接收端的接收窗口、拥塞窗口大小
  - 接收窗口：取决于接收方应用、系统、硬件的限制
  - TCP是双工协议，因此会话双方其实都会各自维护一个发送窗口和一个接受窗口

### 流量控制

- 流量控制一般借助滑动窗口来进行，发送方根据接受方所提供的窗口大小以及应答数据包，可知自己目前还能发送的数据量
- 因此发送方可以根据接受方的实际接收能力控制发送数据量

### 拥塞控制

- 为了保护网络尽可能不出现拥堵现象，引入了【拥塞窗口】概念，因此【发送窗口】的大小取决于【接收窗口】和【拥塞窗口】中的最小值
- 如果发送端出现了超时重传，可以认为此时网络出现了拥堵

- **慢启动**：设定一个【慢启动门限】，建立连接后，接收端的【拥塞窗口】大小会从1开始，指数增长直至门限值

- **拥塞避免**：当【拥塞窗口】达到或超过【慢启动门限】时，窗口大小变为线性增长
- 当拥塞窗口大于接收窗口时，对发送端发送窗口大小的控制就完全由接收窗口控制了

# 第四章 IP

## 基础知识

- IP地址 长度为32位，等价为4字节，每个字节间分别以句点隔开，并用十进制书写
- **环回地址**：单个主机上的应用之间进行网络通信所使用的一个默认地址，通常为`127.0.0.1`或`localhost`

## DNS

![dns解析](pics/dns解析.webp)

- 迭代查询：如上图所示，由本地服务器先后向根域、顶级域、权限域发出查询消息，得到对应IP之后返回给客户端
- 递归查询：本地向根域请求，由根域向顶级域请求，顶级域再递归向权限域请求，最后递归返回给本地服务器
- 迭代查询根域只需要进行两次交互动作；而递归查询中，根域会进行四次交互动作，相当与把压力转交给了根域，不太合适
- 实际上在DNS请求发往本地DNS服务器之前，会先查询本地HOST文件，是否由对应的映射关系，如果有，会直接使用
- DNS查询一般使用UDP协议，因为UDP协议开销小，性能更好。但如果数据包大于MTU时，也只能选择TCP来传输DNS查询和响应
